# OLORIC v0.3 Pipeline Fix Report: Task & Instruction Preservation

**Date:** 2026-09-26  
**Branch:** `experiment/v0.3-development`  
**Status:** Verification Complete  

---

## 1. Executive Summary

During the root-cause audit of OLORIC v0.2 (`docs/v0.3-root-cause-audit.md`), a fundamental architectural defect was discovered in the training and evaluation prompt formatting pipelines:
1. `src/oloric/formatting.py::_format_chatml()` constructed ChatML prompts using only system framing, learner state, document context, and conversation history—completely dropping `model_input.task` and root `example["instruction"]`.
2. `src/oloric/evaluation.py::evaluate_example()` instantiated `OloricModelInput` solely from `example["context"]`, completely stripping `example["instruction"]` and root task metadata.

Because conversation contexts across different benchmark/training records were often identical or similar (e.g. a student expressing confusion), dropping `task` and `instruction` caused distinct pedagogical tasks (such as `follow_up_questions`, `practice_questions`, `misconception_detection`, and `resolve_confusion`) to produce **identical model prompts**. The model was trained without knowledge of the requested tutoring task, directly causing the severe task-following collapse observed in v0.2 (where 16/20 benchmark examples defaulted to `concrete_example`).

This pipeline has now been fixed end-to-end. Both training and evaluation now share the identical input resolution pipeline, preserving `task` and `instruction` into the formatted prompt across all prompt templates while maintaining full backward compatibility.

---

## 2. Root Cause Analysis

### Defect 1: Formatter Dropped `task` and `instruction`
In v0.2:
- `_build_system_message()` accepted `OloricModelInput` but only emitted document context, learner state, and current goal. It completely omitted `model_input.task`.
- `OloricModelInput` lacked an `instruction` field altogether, meaning root-level instructions (`example["instruction"]`) had no schema representation and were ignored.
- In `_format_chatml()`, only the system message and conversation turns were appended. Any task directive not explicitly in conversation turns was lost.

### Defect 2: Evaluation vs Training Path Divergence & Field Stripping
In v0.2:
- `evaluate_example()` constructed the model input via:
  ```python
  context = OloricModelInput(**example["context"])
  ```
  Since `instruction` was stored at the root of benchmark examples (`example["instruction"]`) and `category` was stored at the root (`example["category"]`), `OloricModelInput` received only what was nested in `example["context"]`. Inside `example["context"]`, `task` was often set to the default placeholder `"resolve_confusion"`.
- Consequently, benchmark examples requesting `follow_up_questions` or `practice_questions` presented the model with a prompt stating `"resolve_confusion"`, with zero instruction text.

## 5. Evaluation-Path Parity

In v0.2:
- Training path generated prompts via `build_prompt_and_target(example_dict)`.
- Evaluation path generated prompts via `evaluate_example(example)` which called `engine.generate_response(context)` where `context = OloricModelInput(**example["context"])`.

In v0.3:
Both paths utilize `example_to_model_input()`:
```python
# In training:
model_input = self.example_to_model_input(example_dict)
prompt_text = self.format_input(model_input)

# In evaluation:
context = engine.formatter.example_to_model_input(example)
model_output = engine.generate_response(context)
```
As verified by `test_eval_and_train_path_prompt_equivalence`, `train_prompt == eval_prompt` is bit-for-bit identical for any given example record.

## 7. Backward Compatibility Assessment

1. **Pydantic Model Compatibility**:
   - `instruction: Optional[str] = Field(default=None, ...)` ensures existing serialized models, checkpoints, or cached datasets without `instruction` validate without error.
2. **Fallback Resolution Hierarchy**:
   - In `example_to_model_input`:
     - If `task` is missing or is the generic `"resolve_confusion"`, it checks `example["category"]`, then `ctx["task"]`, then `example["instruction"]`, before falling back to `"resolve_confusion"`.
     - `instruction` is extracted from root `example["instruction"]` or nested `context["instruction"]`.
3. **Template Rendering**:
   - If `instruction` is `None`, no `- Instruction:` line is added to the system prompt, preserving the clean structure of unguided queries.

---

## 8. Remaining Risks and Guardrails for v0.3 Dataset Rebuild

1. **Prompt Length Management**:
   - Adding task and instruction increases prompt length by ~20–40 tokens. Sequence length limits during tokenization must be kept at 2048 to avoid truncating response targets.
2. **Dataset Generation Realignment**:
   - The generator in `scripts/generate_synthetic_dataset.py` must ensure that target actions and strategies strongly correlate with the designated `task` and `instruction` (e.g. `practice_questions` must produce practice exercises with `strategy="guided_inquiry"` or `action="question"`, avoiding the generic `concrete_example` default).
3. **Benchmark Preservation**:
   - Per baseline rules, `evaluation/benchmark.jsonl` remains completely frozen and unchanged.
